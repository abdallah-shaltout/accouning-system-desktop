## 9. Open questions (→ decisions in `00-MASTER-PLAN.md`)

- **`nationalAddress` vs `structuredAddress` — still open, deliberately not closed here.** `Address`'s own doc comment (`address.ts:1-8`) says it "replaces `NationalAddress`" and marks the older type "deprecated," which is real evidence of an intended direction. But this is only a *type-file* annotation: `settings.md`'s `Branch.nationalAddress` and `parties.md`'s `PartyCommon.{nationalAddress,structuredAddress}` both still exist and are both still read/written by the mock today, and nothing in `address.ts` itself (or anywhere in this module's own service files) performs or triggers a migration between them. Deciding whether `structuredAddress` should supersede `nationalAddress` outright (dropping the legacy field from the entity), or whether both must persist indefinitely for backward compatibility with data captured before the picker existed, is a data-migration/product decision for `parties.md`/`settings.md`'s Part 02-B entity design (and D10's importer, which will need to know which field(s) to carry over from the IndexedDB snapshot) — not something this file's own contents can resolve unilaterally. Recommendation for whoever makes that call: since `Address` already stores both an id and a name snapshot per level (built specifically so a printed document never retroactively changes), the pragmatic answer is likely "persist both during a transition window, default new writes to `structuredAddress` only, and drop `nationalAddress` from the schema in a later migration once every existing party/branch has been backfilled" — but this is a recommendation, not a decision made here.
- **`getInsightsFor`'s function-typed `predicate` parameter has no direct Rust equivalent.** Not a design fork so much as an implementation note for whoever writes the Rust commands in Part 03: don't try to port `getInsightsFor` itself 1:1: it's a generic TS-side filter helper over an already-fetched list. Every real caller should get its own concrete, named Rust command (the way `getInsightsForEntity` already does) instead. Flagged for awareness, not requiring a decision now.
- **`TopCustomerRow`'s ranking includes gross sales, not net-of-refunds, unlike `HomeKpis.netSales`.** A minor, pre-existing inconsistency between two dashboard widgets computing "how much did this customer buy" two different ways. Cosmetic (a ranking widget, no accounting consequence) — noted for Part 03's SQL so it isn't "corrected" into matching `netSalesFor`'s refund-netting by accident, which would silently change the widget's existing behavior. No decision needed unless product wants the two to agree.
