> stocktake v2, expiry) and branch transfers (docs/v2/07-products-and-inventory.md). This is the
> module that owns the `stock` shared-manager reach: every quantity/value change in the whole app —
> sales, purchases, refunds, adjustments, stocktakes, transfers — funnels through this module's one
> primitive, `applyStockChange` (`backend/core.ts`), which is this review's single most
> load-bearing function even though it's not itself a service endpoint.

## 5. Concurrency under D8 (several terminals on one DB)

| Race | Rows | Settled by |
|---|---|---|
| Two terminals create a product with the same SKU or barcode at once | `products.sku` / `products.barcode` | `UNIQUE` constraint on both columns; the losing transaction's constraint violation maps to the same `CONFLICT` `AppError` the mock's pre-check throws. The pre-check itself (`db.products.some(...)`) is **not** safe under concurrency in a real DB — the constraint is the real guard, the app-level check is just a nicer error message on the common case. |
| Two terminals save a category/unit/price-list with the same name at once | `categories.name` / `units.name` / `priceLists.name` | Same pattern: `UNIQUE` constraint (case-sensitive exact match per the mock's `trim()`-only normalization — no case-folding today, so the constraint should not case-fold either, to stay byte-identical with the mock's behavior) backstops the pre-check. |
| Two terminals both call `suggestSku(prefix)` and then both `createProduct` with the suggested SKU | `products.sku` | `suggestSku`'s `MAX(existing)+1` is a read-then-suggest, not a reservation — exactly the same non-atomic shape as `parties.md`'s flagged `nextCode()`. The actual safety net is `createProduct`'s own `UNIQUE(sku)` constraint: the second terminal's create fails with `CONFLICT` and the UI re-suggests. **Not a silent-double-write risk** (unlike a document-number counter, a rejected duplicate SKU just makes the user pick another — no financial consequence), so this is lower priority than `nextCode()`/document numbering, but still worth a decision note in §9 about whether Rust should route `suggestSku` through `shared::numbering`-style locking anyway for a smoother UX (no forced retry) versus leaving it as "occasionally races, user retries." |
| Two terminals both create a `StockAdjustment`/`StockTransfer`/`StockCount` at the same instant | `counters.adjustment` / `counters.stockTransfer` / `counters.stockCount` (document numbering) | Standard `shared::numbering` mechanism — `SELECT … FOR UPDATE` on the counter row inside the same transaction as the insert, exactly like every other document-number sequence in the app. **`createTransfer`'s number is one shared counter across all branches** (§1/§2) — the same locking row is contended by every branch's transfers, not partitioned per branch; if branch-partitioned transfer numbering is ever wanted, that's a behavior change beyond this port, not assumed here. |
| Two terminals apply a `StockAdjustment`/transfer-send/transfer-receive against the **same product's** stock at (near) the same instant | `products.stock_qty`, `products.stock_value`, `products.cost_price`, `product_branch_stock` | This is the sharpest race in the whole module: `applyStockChange` reads the product's current `stockQty`/`stockValue`, computes a new average cost, and writes all three back — a classic read-modify-write. Under D8 this **must** run inside the same transaction as a `SELECT … FOR UPDATE` on the product row (locking it for the duration of the adjustment/send/receive/reject), so two concurrent movements on the same product serialize instead of one silently overwriting the other's average-cost recalculation. This is the single most important lock in `shared::stock::apply_change` — every caller (this module, `sales`, `purchases`, `refunds`) depends on it holding, not just this module's own writers. |
| `sendTransfer`'s "enough stock at the source branch" check racing another concurrent send/sale from the same branch | `product_branch_stock` (source branch row) | The availability check (`qty > available + 0.0001` → `CONFLICT`) must be evaluated **inside** the same locked transaction as the stock decrement above — otherwise two concurrent sends could each see "enough" stock, both proceed, and the branch goes negative (or the app-level qty and the row diverge). Same lock, same transaction as the general product-row lock above; no separate mechanism needed if that lock is taken first. |
| `completeAdjustment`/`completeStockCount` re-deriving lines from a **snapshot** (`systemQty` at draft-creation or count-start) vs. current stock at completion time | `stock_adjustments.lines[].system_qty` / `stock_counts.lines[].system_qty` (already-stored snapshot values, not re-read) | No race here **by design** — this is exactly why the snapshot exists (A5): completion always uses the value captured at start, so a sale that happened on this terminal or another terminal between draft/count creation and completion cannot corrupt the delta being applied. No additional lock needed beyond the row lock on `apply_change` itself when the delta is finally applied. |
| Two terminals both attempt `deleteCategory`/`deleteUnit`/`deletePriceList`/`deleteCustomFieldDef` on a row that a third terminal is concurrently assigning to a new/edited product | `categories`/`units`/`priceLists`/`customFieldDefs` vs. `products` (or `users` for price lists) | The reference-check-then-delete pattern needs the delete's reference check to run against a **consistent snapshot** relative to the product/user write — a `SELECT … FOR UPDATE` on the category/unit/price-list/custom-field row (to serialize concurrent deletes of the *same* master-data row) is sufficient; the actual foreign-key-like reference check is a `COUNT(*)` query that MariaDB's normal read-committed-or-better isolation handles correctly as long as the deleting transaction holds its own row lock for the duration — no cross-table lock needed since a product being saved with a stale category id is caught by the product write's own FK constraint (if the category was deleted between the product form loading it and saving), not by the delete side. |
