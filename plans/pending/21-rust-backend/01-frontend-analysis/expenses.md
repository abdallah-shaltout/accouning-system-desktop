> **Status:** done (2026-09-27) · **Inventory:** `docs/backend/contract/expenses.md`

> The simplest posting module reviewed so far (docs/v2/09-purchases-payments-expenses.md §4):
> a one-shot, one-line "spend money" document — Dr expense account [cost center] + VAT input /
> Cr a settings `PaymentMethod`'s system-role account (cash/bank/card/wallet clearing) **or** Cr
> `payable[supplier]` when bought on credit — plus a template/due-list mechanism for recurring
> expenses (rent, subscriptions) that always requires a manual click to actually post, regardless
> of its own `autoPost` flag (§8/§9). This module owns the `ExpensePaidFrom` discriminated union
> (`{ kind: 'method'; paymentMethodId } | { kind: 'credit'; supplierId }`) that `settings.md`'s
> `deletePaymentMethod` reference-check and `payments.md`'s/`vouchers.md`'s settlement-account
> concept already know about — cross-referenced below, not re-derived.

## 5. Concurrency under D8 (several terminals on one DB)

| Race | Rows | Settled by |
|---|---|---|
| Two terminals post an expense (`createExpense` or `postDueRecurringExpense`) at the same moment | `counters.expense` (`nextNumber('expense')`), `journalEntries` | Same "shared counter, prefixed" pattern documented in every prior posting module (`purchases.md`, `products.md`, `vouchers.md`) — Rust needs the counter row locked (`SELECT ... FOR UPDATE`) for the duration of allocate-and-increment. No document-level state is read-then-written beyond the counter (unlike `payments.md`'s allocation race or `vouchers.md`'s settlement race), since an expense never reads or updates any other document's balance — this module has the **simplest** concurrency profile reviewed so far. |
| Two terminals both call `postDueRecurringExpense(id)` on the same due template at nearly the same moment (e.g. two accountants both click "تسجيل الآن" on the same recurring-expense insight before either's page refreshes) | `recurringExpenses.nextDate`, and a doubled `expenses`/`journalEntries` write | **A genuine new race this module introduces** — nothing in `postRecurringExpense` locks or re-checks the template's `nextDate`/due status between the initial `dueRecurringExpenses()`-driven UI read and the actual `postDueRecurringExpense(id)` call; the function only checks the template still *exists* (`النموذج غير موجود`), not that it's still *due*. Two concurrent calls would post the expense **twice** and advance `nextDate` by two months instead of one (the second call's `nextMonthDate` reads the row *after* the first call's `mutate()` already advanced it, if serialized — but if both transactions read the pre-mutation `nextDate` before either commits, both compute the same `nextMonthDate`, and the row ends up only one month ahead despite two `Expense`s having posted). Rust's `expenses_post_due_recurring_expense` must take a locking read (`SELECT ... FOR UPDATE`) on the `recurring_expenses` row and re-verify `active && nextDate <= today` inside the same transaction that posts the expense and advances `nextDate`, refusing with `CONFLICT` (or simply `NOT_FOUND`-equivalent "no longer due") if a concurrent call already consumed this due date. This is the module's one real concurrency finding, parallel in shape to `vouchers.md`'s "two terminals settle the same tender group" race, but narrower in blast radius (a duplicate expense line, not a double-credited clearing account, and it's a rare human-double-click scenario rather than a routine multi-terminal operation). |

## 6. Events and side effects

- **Activity/audit rows**: `createExpense`/`postDueRecurringExpense` call `logActivity('expense', ...)` (`expenses.ts:114`), which also writes the structured `AuditEntry` (`core.ts:331`) — the posting path is fully audited, no gap. **`saveExpenseCategory`, `deleteExpenseCategory`, `saveRecurringExpense`, `deleteRecurringExpense` write no activity/audit row at all** — a genuine, confirmed gap (checked by grep: none of the four calls `logActivity`/`logAudit`). This is the exact bug class the task brief named ("writes with no audit trail") and the same one `products.md` found and fixed for 10 catalog master-data functions (categories/units/price-lists/custom-fields) — **left untouched here, not fixed**, for the reason given in §8 (this session's mandate is conservative: `products.md` fixed 2 narrow cases — a reference-check gap and one specific silent delete — not the module's entire audit-trail gap across all master-data writes; the wider "should every settings/master-data CRUD function audit-log" question was explicitly carried forward as a policy decision in `products.md`'s own summary, not resolved function-by-function per module since it's the same design question repeating, not four independent module bugs).
- **Events emitted**: `createExpense`/`postDueRecurringExpense` both emit `ledger:changed` (`expenses.ts:115`) — correct, and consistent with `vouchers.md`'s finding that this module *doesn't* skip the event the way `invoices.md`/`purchases.md`/`payments.md`'s posting functions do. - **Route links**: `recordExpense`'s `logActivity` call uses a path-templated string (`` `/expenses/${expense.id}` ``) — the standard F7 violation shape, tracked in §8 for the shared 01.C pass.
- **Attachments**: `createExpense`/`postDueRecurringExpense` accept `input.attachmentIds` (photo of the bill, per docs/v2/09 §4) and pass them to both the `Expense` row and `postJournal`'s `attachmentIds` (see §2's note on the two copies).

## 9. Open questions (→ decisions in `00-MASTER-PLAN.md`)

- **`RecurringExpense.autoPost` is a persisted, user-facing form field that no backend code ever reads.** The type, the save/read round-trip, and the settings-page toggle (`RecurringExpensesPage.vue`'s "ترحيل تلقائي — بدون الحاجة لتأكيد المحاسب" switch) all exist, but `postDueRecurringExpense` is the *only* way a due template's expense ever gets posted, and it's always an explicit, user-initiated call — there is no scheduler, timer, or "on app start, auto-post every due template with `autoPost: true`" code path anywhere in the mock. The doc that specs this module (docs/v2/09-purchases-payments-expenses.md §4) itself hedges: "the accountant posts it in one click; `autoPost` is optional" — reading this literally, `autoPost` may have always been intended as *only* a note-to-self/reporting flag rather than real automation, or it may be a genuinely unfinished v1 feature. **This is a real product decision, not an implementation detail**: Part 03 could (a) port the field as pure inert state exactly as the mock has it today (simplest, zero behavior change, matches "we don't invent new accounting semantics"); or (b) implement real automation — a background job on the Main PC (D1's "one Main Server per branch" fits this naturally) that posts every `active && autoPost && nextDate <= today` template automatically, which would need its own concurrency handling beyond what §5 already specifies (a scheduled job racing a user's manual `postDueRecurringExpense` click on the same template) and a decision about whether a failed auto-post (e.g. a deactivated payment method) should silently skip, retry, or surface as its own diagnostics/insight alert. **Recommendation if forced to pick now**: (a) for this phase — port the field as-is with zero new behavior, since inventing a background scheduler is a meaningfully larger scope item than anything else in this module and isn't something any other domain in this plan needs yet. Flagged for the user/Part-03 implementer, not silently assumed.
- **Should `Expense.branchId` become a real, end-to-end field** (form → `ExpenseInput` → `recordExpense` → the posted `Expense` row), so a multi-branch deployment can tell which branch an expense document belongs to at the document level, not just infer it from whichever branch the journal-line default resolves to? Today it's inert (§2/§8). This is a scope question for whoever designs the `expenses` domain's DTOs in Part 03 (adding the field is low-risk and non-breaking — an `Option<Uuid>` with the same `DEFAULT_BRANCH_ID`-style fallback everything else uses — but it does mean touching `ExpenseInput` and presumably the expense form page, which is out of this plan's scope to decide unilaterally). No accounting bug exists today (the journal entry still resolves a branch correctly via `postJournal`'s own default), so this doesn't block the gate; it's a note for Part 03.
- **Should `splitTax`'s silent `rate = 0` fallback for a missing/inactive `taxId` become a hard `VALIDATION` throw instead?** (§3/§8). Not decided here because it's genuinely ambiguous whether the expense form already prevents this state from reaching the service layer — deciding requires either reading the form page (out of scope for this plan) or a product call on whether "isTaxInvoice but no valid tax selected" should ever be postable at all. No `verify:mocks` invariant catches this today, and nothing in the reviewed code exercises it, so it's not a proven bug, just a plausible one — left open rather than guessed at.
