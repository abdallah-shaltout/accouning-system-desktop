Not a bug to fix here (this is read-only display rounding, no accounting consequence), but worth a note: don't let this module's 2dp qty rounding leak into how Rust picks a *storage* scale for `products.qty` — that decision belongs to `products.md`, already made there. This module's `round2(v.qty)` is purely a display-rounding choice for the dashboard chart, unrelated to the ledger. |

No `_uuid_`/`_date_`/`_route_`/`_enum_` hints apply anywhere in this module's output — every field is either a plain string label (weekday name, payment-method name, "أخرى" fallback), a count, or money/percentage.

## 3. Validation and errors

**None.** No function in this module throws an `ApiError` (or any error) under any input — every edge case (no data in the window, `recent.length === 0`, `totalRevenue === 0`, division by a possibly-zero denominator) is guarded with a ternary that falls back to a zero value or a fixed "لا توجد بيانات كافية بعد" ("not enough data yet") / "لا توجد مبيعات كافية بعد لهذه الفترة" Arabic string, never a thrown error. `days`/`limit` have JS default parameters (`= 30`, `= 8`) but **no upper/lower bound check** — a caller passing `days: -5` or `days: 100000` would not be rejected, just produce a degenerate (empty or very long) trend array. **Flagged in §8** as a low-risk, easy hardening for the Rust command layer, not a mock fix (the mock's permissiveness here has never caused a bug since only trusted internal UI code calls these functions today — but an IPC command should validate its own inputs regardless of who calls it, per master plan F8).
